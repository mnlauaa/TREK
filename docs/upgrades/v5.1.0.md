# TREK v5.1.0 fork upgrade

This branch ports the TREK fork onto official v5.1.0. The follow-up reconciliation includes release commit `f416f27e30f313959b36af1abbb9a6d15ea24e6a`, which contains the itinerary timing and deployment changes. The original checkout remains untouched. It does not deploy or modify a production database.

## Pinned inputs

- Official v5.1.0 commit `dc36c21c08f681fd2806764fad8e17b270f6f175`.
- Initial fork baseline `origin/dev` commit `0b970eac7aad7ccc38d5a505c1c0d5866f919dd1`.
- Current release customization baseline `f416f27e30f313959b36af1abbb9a6d15ea24e6a`. The [release inventory](v5.1.0-release-inventory.md) accounts for its 113 changed paths beyond the initial baseline.
- The official release and remote tag were checked. The tag and commit are unsigned. This is provenance verification, not signature verification.
- The conflict rehearsal found 416 unique conflict paths. The port starts from the release tree and adapts retained features to the v5 repositories and transactions.

## Retained behavior

The port retains layered and frozen exchange rates, deliberate preview/apply conversion, common currencies, Guest identity transfer, encrypted Web Push devices, departure countdown, mobile timeline recovery, payment editing, Traditional Chinese support, neutral notices and source links, community MinIO CI, and opt-in fork Sonar.

Legacy foreign expenses without a trusted frozen rate remain awaiting conversion. Opening Costs does not freeze them. Historical null-currency payments retain their shipped display-currency meaning. Newly recorded payments that default to the trip currency store that currency explicitly.

One Web Push channel handles encrypted registrations. Old `push` channel settings map to `webpush`. Existing fork preferences win collisions. Native upstream plaintext subscriptions are retained but require browser re-registration; they are not guessed into encrypted device records. The legacy `WEB_PUSH_VAPID_*` environment aliases remain supported.

## Database upgrade

Published upstream migration files are unchanged. The appended ORM migration `Migration20200101046330_adopt_fork_schema_lineages` adopts the original four fork migrations. A second appended migration, `Migration20200101046340_adopt_itinerary_timing`, adopts `fork/itinerary-timing-v1`. Existing IDs, timestamps and stored values remain unchanged. The preflight recognizes both the earlier four-ID ORM generation and the current five-ID release generation. Startup reads the source catalog before creating ORM bookkeeping, takes a snapshot before any migration write, then applies normalization and migrations in one transaction. Unknown or inconsistent histories fail before writes. Direct ORM CLI replay of a positional database is refused.

Committed populated fixtures exercise fork positions 180, 199, 202 and 244, plus native legacy 258 and the populated current-release itinerary schema. Tests cover repeated startup, protected values, snapshot failure, late foreign-key failure, transaction rollback and retry on the same connection. The audit script opens databases read-only.

Run the read-only readiness audit with:

```sh
cd server
npm run audit:v4-upgrade -- --db /absolute/path/to/trek.db
npm run audit:v4-upgrade -- --db /absolute/path/to/upgraded-copy.db --require-current
```

## Production rollout gates

Upstream v5.1 defaults `TREK_SERVICES` to `auto` and may register the instance with TREK services. Review that choice before promotion; set `TREK_SERVICES=off` if this instance must not register. Local container rehearsals disable it and have no network access.

Before promotion, rehearse against a recent production backup with the actual encryption key and installed plugins. Verify uploads and storage configuration, then inspect the read-only audit. These local synthetic fixtures do not prove production data or plugin compatibility.

Retain a consistent pre-upgrade database and upload backup. Roll back by stopping the new version and restoring that backup with the previous image. Do not point the previous image at an upgraded database. No production rollout, push or PR is part of this local implementation.

## Design decisions

Model the Domain kept fork migration identities separate from upstream migration positions. Outcome-Oriented Execution kept v5 repositories and transactions as the final architecture. Exhaust the Design Space compared migration strategies before selecting the release-baseline port. Build the Lever produced populated migration fixtures and read-only audits. Laziness Protocol removed superseded code and used the existing trip store for refresh events.

## Current release reconciliation

The latest release adds per-visit fixed times and stays, day timing preferences, directed manual travel durations, and the fifth stable fork migration `fork/itinerary-timing-v1`. These contracts use v5 repositories and transactions. REST, MCP, offline edits, trip copies, public sharing and PDF views retain the separate visit and booking semantics. Deployment files retain backup hooks, non-root runtime and network restrictions. The startup probe now allows ten minutes for snapshots and migrations before steady-state liveness begins.

Reproduce the populated current-release fixture with `node server/scripts/build-release-timing-fixture.mjs`. This requires the system `git`, `tar` and `sqlite3` commands and installed project dependencies. The script archives the pinned release and runs its real database initializer before adding synthetic timing data.

Rehearse a built image with `python3 scripts/upgrade/rehearse-release.py --image IMAGE --output NEW_DIRECTORY`. Run with the project's Node version on `PATH`. The script creates disposable fresh and release databases, uses the workload's non-root identity and startup command, disables network access, and stops its containers after recording health, read-only audits and preserved values. It does not access production data.
