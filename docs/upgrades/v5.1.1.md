This upgrade starts from refreshed `origin/dev` at `020a51a00968052f1bf1de16c9533b8727a8edcd` on `codex/upgrade-trek-v5.1.1`. ## Upstream push cutover

On 2026-11-09 the user clarified that the custom push implementation was intended for iPhone notifications and requested replacing it with upstream v5.1.1. This supersedes the earlier push disposition and native-enrollment limitation above.

The active client API, permission hook, desktop/mobile settings cards, native prompt, service-worker payload, server registration/controller/dispatcher, VAPID service and Watch sender now follow official v5.1.1. The native iOS/Android source already matched upstream. The fork device-management UI/API, invitation, encrypted subscription repository/entity, custom schemas and `WEB_PUSH_VAPID_*` configuration aliases are removed. Other fork features remain intact. Upstream still encrypts its stored VAPID private key.

The forward migration `Migration20200101046370_retire_fork_web_push` preserves saved opt-outs and admin defaults, maps `webpush` to `push`, and clears stale official device registrations once. Current fork preferences win collisions with older mirrored `push` values. New registrations survive subsequent startup. Published migration files are unchanged; the legacy encrypted table and five historical fork IDs remain for lineage/audit and offline encryption rotation, with no runtime sender reading that table.

Users must enable notifications again. A bounded browser cutover guard serializes retirement across tabs and clears old browser registrations. An origin-local cache records only the endpoint explicitly enrolled through upstream after cutover. Page resync and service-worker renewal reject unknown or delayed legacy endpoints, preventing revoked registrations from becoming active again. Native registration bypasses this browser-only transition. Storage/locking failure leaves browser enrollment closed for retry. This is transition bookkeeping, not a second push channel or device-management API.

Operators using removed aliases must use upstream `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`, keeping a complete key pair together. Otherwise upstream uses the existing encrypted database key pair. An administrator must enable the `push` channel; users sign into the installed native app, choose **Turn on** when prompted, and allow the OS permission, or use Settings → Notifications later.

Cutover validation is recorded separately from the pre-cutover broad suites. Actual APNs/FCM delivery requires an installed native build and relay/device credentials and is not claimed by local tests. No Docker containers were recreated, no production database was used, and nothing was pushed or deployed for this follow-up.

## Rollout gates

A fresh production-backup restore with real encryption material, storage and installed plugins remains required before production. Local tests use disposable data with `TREK_SERVICES=off`. Production writes require maintenance, a complete backup and an explicit rollback image. Rollback restores old image and pre-upgrade data together. No live production evidence is claimed.
